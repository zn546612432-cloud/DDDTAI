# DDDTAI 统一手机运行框架

状态：设计与迁移契约，尚未实现完整运行系统。

## 目标与保留范围

DDDTAI 是新开发目标；BBBTAI 保留作可运行对照。新核心替换旧控制逻辑，不通过复制旧 main.js、保留多组 tick 再包一层入口来宣称统一。

保留已确定的手机外观、各 App 界面、图标、头像、照片、音频、历史聊天、朋友圈正文、人设和对话示例。剧情文本迁移时保持稳定 ID，不重新生成。55 天范围与 D01=2025-05-19、D55=2025-07-12 保留。

首个源基线：zn546612432-cloud/BBBTAI，595dd14ab58169c2aa8656fc3d3ad7d980063d07（PR #80）。后续采纳其他分支时单独记录来源和差异，不以旧架构说明文件中的过期完成状态为依据。

## 分层与写入权限

| 计划目录 | 唯一职责 | 禁止行为 |
|---|---|---|
| src/app | 启动、组合依赖、前后台生命周期，唯一运行循环 | 放当天台词、复制每日计时器 |
| src/core | 命令校验、事务、事件记录、去重、运行状态 | 依赖 App DOM、调用模型 |
| src/domains/time | 唯一游戏时钟、时间推进计划和阻挡边界 | 由 App 或每日剧情改流速 |
| src/domains/power | 普通耗电、短充额度、长充和终章电量策略 | 自行推进日期、绕过剧情许可 |
| src/domains/story | 事件登记、前置、必做分类、完成证据、阻挡点 | 用日期经过代替玩家完成 |
| src/domains/messaging | 投递队列、气泡写入、实际发送、预设选择、迟回、历史、未读 | 各 App 直接 messages.push 或自行加未读 |
| src/domains/commissions | 接单、授权、阶段进度、提交、验收 | 每天再写一套委托状态机 |
| src/domains/ledger | 入账、支出、收据，事务 ID 防重复结算 | 邮件或小游戏直接改银行余额 |
| src/domains/facts | 记录已经发生的事实，给联动和 AI 提供经过过滤的读取 | 把未来正文、未发送草稿当事实 |
| src/domains/journal | 朋友圈、日记、备忘录等内容可见性和事实依赖 | 通过 UI 临时判断某次赴约是否发生 |
| src/integrations | AI、语音合成、持久化等外部适配器 | 直接修改剧情完成、时钟、未读和余额 |
| src/apps/<app>/<feature> | 各 App 的界面、路由和用户命令 | 实施时间、奖励、剧情规则 |
| src/content | 分天/角色/任务配置和资产映射 | 导入 DOM 或运行服务、启动计时器 |
| src/developer | 内容编辑、测试重建、状态诊断 | 与正常游玩共享隐式自动完成权限 |

用户操作 → 命令校验 → 领域规则 → 原子提交事实及事件 → 界面读取结果。外部模型产出也作为输入命令进入这一条路径，不直接写聊天。

不要求不同领域共用一个巨大函数；要求每条规则、每种事实的写入只有一个权威来源。

## 剧情事件必须显式分类

| 类别 | 正常时间推进 | 允许自动产生的结果 |
|---|---|---|
| required | 到指定阻挡点停住，实际操作完成才放行 | 不自动完成、不代发、不自动通关 |
| required-by-deadline | 开放日至截止点可继续推进；截止点未完成必须停住 | 不因开始部署、读邮件就视为完成 |
| ambient | 可跨过 | 独立发生的 NPC 内容可静默归档 |
| optional-timed | 可错过，有效期后进入收尾或迟回 | 只产生已配置的未响应结果，不能当成赴约 |
| optional-contract | 可不接；接后按有效期处理 | 不自动通关、提交、结算 |
| terminal | 按终章专用顺序推进 | 只接受指定录音播放结束、充电、解锁等证据 |

“台词固定”与“不可跳过”分别配置。日常可以使用固定台词但允许错过；必要主线也不是每条 NPC 气泡都必须由玩家点击。

事件至少包含：稳定 ID、类型、触发时间/条件、依赖事件、完成条件、阻挡点、历史策略、迟回策略、过期策略、允许产生的结果、版本与迁移规则。不能靠某个开发者记得它属于主线。

事件发生、消息已送达、玩家已读、玩家已发送、任务已成功、已经结算是不同事实。完成条件必须明确引用相应事实。

## 时间推进的统一流程

1. 自然走时、主画面挂机、短充、长充都先申请推进到目标时间。
2. 核心读取所有可能跨越的事件，按游戏时间、因果依赖和稳定顺序检查。
3. 找到最近的未满足强制阻挡点，将实际可到达时间裁剪到这里。项目开放日与最后完成日分别处理，不能从开放日起锁住整段日期。
4. 对已经越过的普通事件执行历史/过期策略；不能越过未发送的熙蒙台词补出依赖回复。
5. 原子提交实际到达时间、时间引发的事件、实际耗电和可见状态；重复执行不得重复发消息或发钱。
6. 到达阻挡点时停止继续跳时，保留手机操作和相关入口；满足真实完成条件后再放行。

禁止越过剧情点与禁止充电是独立权限。普通主线可以限制推进而允许补电；确实禁止充电的剧情和终章使用显式策略。不能仅因主线未完成就默认整天禁止短充。

保留已确认倍速：所有 App 内现实 1 分钟=游戏 5 分钟，解锁主界面无交互挂机现实 1 秒=游戏 5 分钟。后台暂停游戏时间；消息间隔和小游戏倒计时使用现实时间。短充不借重构擅自改变倍速、+10%额度或普通跨日语义。

## 全渠道消息

微信、Mirage、NoApp、短信、固定主线、普通预设及 AI 产出共用同一条写入和投递入口。每条气泡有来源事件、稳定/幂等 ID、原发生时间、实际投递时间和投递模式。

- 当前场景：共享会话队列，按现实间隔逐条送达；离开会话不重新启动一套旧计时器。
- 历史补齐：静默、不占今日通知队列，保留原日期；只补已经成立的 NPC 前缀。
- 熙蒙的话：只能由实际发送命令产生。机房升级、勾选提醒、收邮件都不能代发。
- 迟回：当天/隔天/多日/事情已解决由游戏时间与事实共同选择；旧草稿让位于当前有效场景。
- 未读：每条已送达 NPC 气泡按会话计数；打开对应会话清零，不误清其他会话。
- 通知：所有来源共用队列和过期取消机制；通知中心的未读存在不代表旧通知应该重新弹出。
- AI：保留人设、温度、语音、追问、电话和去重规则；模型生成与手机投递分层。跨天未发出的 AI 结果不能伪装成昨天已经发生的聊天。

## 委托和跨 App 结果

所有委托使用同一状态流：发布 → 接单 → KIRA 单附件 → 文件预览 → GHOST 授权与执行 → READY TO SUBMIT → 实际提交 → 验收/结算。

不同日期仅配置发布者、正文、等级、截止时间、阶段类型、数量、耗时及金额。D01 无游戏的部署环节、既有数据修复以及 Flow 工具测试通过明确的任务类型/策略表达，不能为统一而改掉用户已确认的玩法。

任务结果先提交成功事实；银行账本按唯一结算 ID 入账；邮件、回执、朋友圈和日记读取真实事实。重载和重试不重复结算。错过晚饭邀约不会产生一起吃过饭的照片或朋友圈。

## 存档、迁移和开发者工具

- 新仓库使用独立命名空间；部署后不覆盖 BBBTAI 的存档。
- 提供显式旧存档导出/导入及版本迁移，不假设两个地址可以互相读取本地状态。
- 正式旧记录导入保留日期、消息 ID、资产引用、已发回复和结算凭据。
- 开发者跳日可以有“测试重建”模式，但必须显式标记模拟完成，先备份；普通短充/长充没有该权限。
- 配置静态检查：缺少必做分类、未知引用、循环依赖、不可能的完成条件、缺失附件/资产、重复结算 ID、可选事件误阻挡，都应在构建时发现。
- 运行时诊断能解释：为什么停住、等待哪个事件、需要哪种真实操作、最近一次实际推进到哪里。

## 统一完成的判定

旧控制入口必须有逐项替换记录，并通过行为验收。仅入口改名、把旧 tick 放入一个循环、增加一份新配置但仍让旧控制器同时运行，都不算迁移完成。
